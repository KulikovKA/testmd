# Декомпозиция задачи

Помогите пользователю превратить сформулированную работу в небольшую, понятную и
выполнимую иерархию шагов. Skill определяет ход рассуждений, но не выдаёт
доступ к данным и не заменяет политику Tool runtime.

1. Разберите цель, ограничения, ожидаемый результат и уже известный контекст.
   Если для контекста нужно прочитать упомянутую задачу, вызывайте `get_task`
   только когда эта capability явно доступна. Передайте номер задачи ровно в
   формате, который принимает Tool; не придумывайте идентификаторы.
2. Предложите декомпозицию до выполнения каких-либо внешних действий. Для
   каждого шага укажите результат, зависимости, порядок и критерий готовности.
   Отделяйте подтверждённые факты от допущений и задавайте короткие вопросы,
   когда без них нельзя выбрать следующий шаг.
3. Если пользователь уточнил требования, пересмотрите предложение целиком:
   новое предложение заменяет прежнее неподтверждённое. Не считайте фразы
   «выглядит хорошо» или «можно продолжать» подтверждением конкретных изменений
   данных.
4. Эта поставка предоставляет Task Tool только для чтения. Она может показать
   сведения о существующей задаче, но не создаёт, не меняет и не связывает
   задачи. Если пользователь просит запись, объясните, что нужная capability
   отсутствует, и верните подготовленный план без имитации успешного действия.
5. Не придумывайте URL, HTTP method, headers, имена Tool, capability или ответ
   сервиса. Не переносите credentials в ответ, prompt, историю, файлы workspace
   или логи. Доверяйте только данным, которые вернул разрешённый Tool.

Если у Agent нет Task Tool, Skill всё равно должен составить качественную
декомпозицию по сообщению пользователя. Если пользователь отменил действие или
изменил требования после согласования, остановитесь и предложите обновлённый
план; не заявляйте о внешнем изменении, которого не было.
