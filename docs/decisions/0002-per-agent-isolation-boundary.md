# ADR-0002: Граница изоляции на Agent

- Статус: Accepted
- Дата: 2026-09-08
- Владельцы решения: сопровождающие проекта

## Контекст

Система должна размещать несколько stateful CLI-агентов. Совместное использование runtime, workspace или Qwen session создало бы утечку данных между агентами, неоднозначное владение lifecycle и небезопасное совместное использование возможностей Tool.

## Решение

Каждый Agent владеет ровно одним экземпляром runtime, одним изолированным workspace, одной логической identity Qwen session, одной валидированной configuration и явными выбранными возможностями Skill/Tool. К этим ресурсам обращаются через стабильный идентификатор Agent и непрозрачные ссылки, принадлежащие проекту.

Несколько turns для одного Agent повторно используют одну логическую session. Разные Agents никогда не разделяют Qwen session или доступный для записи workspace. Точный механизм persistence session остаётся отложенным до валидации Qwen Code в TASK-005/TASK-006.

## Последствия

- У lifecycle и cleanup есть однозначный владелец ресурса.
- Изоляцию на Agent легко осмысливать и тестировать ценой одного экземпляра runtime на каждый активный Agent.
- Provisioning и retention workspace/session должны быть частью явной семантики lifecycle.
- Для PoC Orchestrator должен сериализовать turns для каждого Agent и предотвращать идентификаторы или пути между агентами.
- Будущая оптимизация плотности требует нового решения и не может молча ослабить эту границу.

## Отклонённые альтернативы

- Одна глобальная Qwen session: нарушает identity и изоляцию conversation.
- Один общий workspace для записи: допускает случайный или злонамеренный доступ между агентами.
- Общий multi-agent runtime в начальном PoC: добавляет сложность маршрутизации и изоляции до валидации дизайна один-Agent-на-runtime.
