# ADR-0001: Граница Runtime-порта и драйвера

- Статус: Accepted
- Дата: 2026-09-08
- Владельцы решения: сопровождающие проекта

## Контекст

Локальная разработка использует Docker, а последующая корпоративная среда — Kata Containers. Их API, идентификаторы, детали жизненного цикла, хранилище и сеть различаются. Если разрешить Agent Orchestrator напрямую вызывать любой backend, инфраструктурные решения распространятся по бизнес-логике, а замена станет небезопасной.

## Решение

Определить принадлежащий проекту порт `AgentRuntime` на границе application. `DockerRuntime` и будущий `KataRuntime` — драйверы, реализующие этот порт. Код domain и application использует только runtime-нейтральные значения запросов/результатов, наблюдения runtime, непрозрачные handles и категории ошибок. Наблюдения runtime отличаются от состояния жизненного цикла Agent, которым владеет Orchestrator.

Первоначальный порт охватывает create, start, status, stop и delete. TASK-002 зафиксирует точные сигнатуры и семантику. Обмен conversation/session использует отдельный runtime-нейтральный interaction port. Любая backend-специфичная операция, необходимая для обращения к агенту, остаётся внутри этого interaction adapter; она не может выполняться Docker/Kata-вызовами в use case Orchestrator.

Выбор runtime и создание драйвера происходят в composition root. Общий conformance suite определяет наблюдаемое поведение для всех драйверов.

## Последствия

- Use cases Orchestrator можно повторно использовать с Docker или Kata.
- Возможности backend должны переводиться в намеренно малый общий контракт.
- Runtime handles и ошибки нуждаются в представлениях, принадлежащих проекту.
- Управление runtime и взаимодействие с агентом требуют раздельных контрактов и тестов, даже если один backend adapter помогает реализовать оба.
- Часть backend-специфичной диагностики может существовать только в логах/деталях adapter, тогда как стабильные категории ошибок остаются переносимыми.
- Добавление Kata требует нового adapter и валидации среды, а не ветвления бизнес-логики.

## Отклонённые альтернативы

- Прямой вызов Docker из lifecycle services: связывает основное поведение с локальным backend.
- Объединённый интерфейс, раскрывающий все возможности Docker и Kata: допускает утечку инфраструктурных понятий и лишает conformance смысла.
- Выбор backend условными ветками во всех use cases: делает тестирование и последующую замену хрупкими.
