# ADR-0004: Владение повторными попытками и восстановлением Runtime

* Статус: Accepted
* Дата: 2026-09-08
* Владельцы решения: сопровождающие проекта

## Контекст

Вызовы жизненного цикла могут потерять ответ после того, как backend уже выполнил побочный эффект. Частичное выделение ресурсов или удаление могут оставить принадлежащие системе ресурсы. Семантика повторных попыток не должна зависеть от backend и не должна приводить к созданию дублирующих runtime, утечке workspace или незаметному восстановлению удалённого Agent. Отмена вызова со стороны вызывающего кода не всегда позволяет вернуть новый выделенный handle.

## Решение

Использовать асинхронный lifecycle-порт с явным timeout для каждого вызова и нативной async-отменой. Идентичность Agent является идентичностью идемпотентности create на протяжении всего его жизненного цикла. Повторные идентичные запросы create разрешаются в одно и то же выделение ресурсов; отличающиеся запросы приводят к конфликту. Успешный delete завершает жизненный цикл этой идентичности Agent.

Driver владеет recovery-метаданными и фиксирует владение до начала выделения ресурсов. Незавершённая работа откатывается в пределах доступного временного бюджета либо сохраняется под восстанавливаемым непрозрачным handle. Повторный вызов create по идентичности Agent восстанавливает незавершённую очистку даже в том случае, если исходный вызов был отменён. Delete считается успешным только после отсутствия всех ресурсов, принадлежащих runtime, включая workspace.

Runtime observations и независимое подтверждение readiness не назначают lifecycle state для Agent. Семантика conversation/session остаётся отдельным портом, как определено в ADR-0001. Подробный контракт описан в [runtime-contract.md](../runtime-contract.md).

## Последствия

* Повторные попытки backend могут быть согласованы без раскрытия infrastructure IDs прикладным use cases.
* Drivers должны хранить записи владения, идемпотентности и удаления достаточно долго для покрытия повторных попыток; реальная persistence/recovery проверяется в рамках задачи каждого driver.
* Timeouts и cancellations могут происходить уже после применения изменений. Вызывающая сторона должна согласовывать ту же идентичность, а не предполагать rollback или автоматически создавать замену.
* После удаления для нового Agent требуется новая идентичность; удалённые идентичности не переиспользуются.
* Общие conformance tests проверяют сценарии ошибок и прерываний через отдельный test harness. In-memory fake не заявляет crash durability.

## Отклонённые альтернативы

* Выделять новый runtime при каждой повторной попытке create: существует риск дублирования runtime и появления осиротевших изолированных данных.
* Отбрасывать ссылки при timeout/cancellation: частично созданные ресурсы становятся недоступными для cleanup.
* Считать cancellation доказательством rollback: это не позволяет корректно описывать race conditions удалённого backend.
* Разрешить create восстанавливать удалённую идентичность: поздний запрос может заново создать Agent, который пользователь уже удалил.
